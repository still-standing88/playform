Major problems in the current MPV adapter
1. The locking is incomplete
The adapter has an RLock, but only some operations use it:
mpv_video_player.py (line 64)

• load_file
• load_url
• subtitle loading
• release
• free
• initialization

• a failed state query returns None;
• get_play_state() may then subscript None;

• the GUI cannot distinguish “paused” from “MPV is dead”.

The MPV adapter calls synchronous python-mpv methods directly. _track_command() only counts calls; it does not throttle, queue, cancel, or coalesce anything.

_update_current_track() is called from the AVPlay monitor callback and updates Qt widgets directly:

Qt widgets should only be modified from the GUI thread. This may not be the direct MPV crash, but it creates another race during rapid track changes.
6. MPV-specific errors are not fully handled
The wrapper handles ordinary Python exceptions, but it does not properly handle:
• MPV event queue overflow;
• late events from a previous file;
• commands after shutdown;
• commands in flight during terminate();
• MPV core failure requiring recreation;
• native access violations or segmentation faults.
A Python try/except cannot reliably recover from a crash inside libmpv. faulthandler can log some failures, but it cannot keep the process alive after a native crash.
Why VLC appears more stable
The VLC adapter is also not fully serialized, so its stability should not be interpreted as proof that the application is thread-safe.
However:
• VLC’s native API appears more tolerant of rapid state changes;
• the VLC calls used here generally do not involve the same python-mpv event-queue behavior;
• the MPV adapter has partial locking, silent failures, and unsafe destruction;
• MPV is receiving synchronous seeks and loads from several application threads.
The likely issue is not simply “MPV cannot be called from multiple threads”. It is the combination of:
1. incomplete serialization;
2. load/seek flooding;
3. destruction while commands are active;
4. stale monitor activity;
5. swallowed errors;
6. lack of recovery after MPV shutdown.

The MPV side should be rewritten around an actor-style command controller:

Important rules:
• All MPV operations, including load, release, subtitle loading, and shutdown, go through one controller.
• Never call mpv directly from GUI code or the playlist monitor.
• Do not swallow exceptions.
• Use a generation number for every load. Ignore events from older generations.
• Stop the monitor before destroying the MPV instance.
• Coalesce seeks so only the newest pending seek survives.
• Debounce slider seeking, for example by 50–100 ms, and always send the final seek on release.
• Coalesce volume, speed, filter, and resize commands.
• Treat a new load as a barrier that clears obsolete pending commands.
• Wait for file-loaded before applying subtitles, seeking, or changing filters.
• Cache time-pos, duration, pause state, mute state, and volume instead of repeatedly performing five synchronous native property calls.
• Forward events to Qt using queued signals; never touch widgets from an MPV callback or monitor thread.
• Register and handle shutdown and queue-overflow.
• If MPV shuts down, mark the backend broken, reject pending commands, and recreate the core.
Process isolation
If the requirement is “even if MPV crashes, PlayForm must remain alive”, then a separate process is the correct solution.
Two possible designs:
Child process containing libmpv
A spawned Windows process imports mpv, creates the MPV instance, and communicates with PlayForm through a bounded multiprocessing.Pipe or named pipe.
Advantages:
• native MPV crashes do not kill the GUI process;
• the parent can detect process exit and restart playback;
• commands remain serialized inside the child.
Disadvantages:
• more IPC code;
• video embedding into the parent Qt window needs testing;
• synchronous API methods become request/response messages;
• packaging becomes more complex.
Separate mpv.exe process
Launch MPV as an external process with a Windows IPC pipe and send JSON commands.
This is the strongest isolation boundary. If MPV crashes, PlayForm sees the process exit and can restart it. The MPV process can potentially render into the Qt window using its HWND.
This is probably the most reliable long-term architecture, but it requires packaging an MPV executable and reimplementing the current wrapper protocol.
Final recommendation
Do this in stages:
1. Build an MPV-specific backend-neutral player factory.
2. Fix the current MPV adapter’s lifecycle and error propagation.
3. Add a serialized, bounded, coalescing command controller.
4. Move playlist advancement and all Qt updates onto the correct threads.
5. Stress-test rapid loads, seeks, next/previous, close/reopen, and shutdown.
6. Only then decide whether MPV still needs process isolation.
Basic VLC-to-MPV substitution is feasible. The current implementation, however, is not stable enough to use as a replacement. The first priority should be fixing the adapter’s command ownership and teardown races; process isolation should be added if native MPV crashes continue after that.

How MPV errors actually work
libmpv has several error layers.
Immediate API errors
C functions return integer codes:
• 0 or positive: success
• negative: error
The official API defines errors such as MPV_ERROR_COMMAND, MPV_ERROR_LOADING_FAILED, MPV_ERROR_UNKNOWN_FORMAT, and MPV_ERROR_EVENT_QUEUE_FULL. Official libmpv client API
The installed python-mpv wrapper converts negative return codes into Python exceptions using ctypes error checking:
mpv.py (line 557)
So this:
python
Copy
mpv.command("seek", ...)
can raise a Python exception.
Asynchronous playback errors
A loadfile command can be accepted successfully, but decoding can fail later. In that case MPV usually reports an end-file event with an error reason/code rather than throwing from the original loadfile call. The MPV manual documents end-file reasons such as eof, stop, and error. MPV input manual
Therefore:
python
Copy
mpv.command("loadfile", path)
returning successfully does not mean the file decoded successfully.
Event queue errors
The python-mpv event thread handles QUEUE_OVERFLOW, but the installed wrapper only forwards that failure to asynchronous command callbacks:
mpv.py (line 973)
The current AVPlay wrapper does not register a queue-overflow handler, so this failure is not properly exposed to the application.
Native crashes
If libmpv, FFmpeg, a decoder, GPU driver, or a DLL performs an access violation or segmentation fault, Python cannot reliably catch it with try/except.
That is the distinction:

bad command/property       -> Python exception

native memory/GPU crash     -> process crash

The adapter also does not configure an MPV log handler, so valuable decoder and core messages are lost.
The “one MPV thread” issue
Your instinct to use one command owner is correct, but the reason is slightly different.
The official libmpv API says:
• the client API is generally thread-safe;
• multiple threads do not provide an advantage because calls are serialized through one internal core lock;
• synchronous operations can block for an unbounded amount of time;
• asynchronous calls can be reordered unless completion is awaited.
Official libmpv client API
So multiple application threads do not make MPV process commands in parallel. They only compete for the same internal lock.
That is why the correct architecture is:
text
Enable word wrap
Copy
GUI threads
    |
    v
command scheduler
    |
    v
one application-owned MPV command worker
    |
    v
libmpv
The scheduler should accept every GUI request, but not necessarily transmit every intermediate state to MPV.
For example:
• load, stop, and release: preserve ordering.
• seek: newest pending seek replaces older pending seeks.
• volume: latest value wins.
• speed: latest value wins.
• filter sliders: latest value wins.
• play/pause: maintain the latest desired state.
• an already-running native command is allowed to finish; it cannot safely be interrupted from another thread.
If every mouse movement during seeking must be executed physically by MPV, the queue will inevitably grow. No wrapper can make a serialized playback core process 200 seeks in parallel. The practical meaning of “every command must go through” should be “every user intent is accepted and resolved”, not “every obsolete intermediate slider position must reach libmpv”.
Also, MPV’s official API explicitly warns that mpv_terminate_destroy() is not safe while another thread is using the same context. Official client API
That is especially relevant because the current adapter calls terminate() in free() while the GUI and AVPlay monitor can still be querying or commanding MPV:
mpv_video_player.py (line 100)
What I would change
The MPV adapter needs:
1. One serialized command scheduler.
2. No direct MPV calls outside that scheduler.
3. Coalescing for seeks, volume, speed, and filter changes.
4. A generation number so events from old files are ignored.
5. Proper end-file, shutdown, and queue-overflow handling.
6. Cached playback state instead of repeatedly issuing several synchronous property queries.
7. Minimal MPV event callbacks that only enqueue data; no GUI manipulation.
8. Stop the AVPlay monitor before releasing MPV.
9. No exception swallowing.
10. MPV logging through log_handler.
This would make rapid commands manageable, but it cannot guarantee protection against a genuine native libmpv or GPU-driver crash.
Separate libmpv process
Since mpv.exe is not acceptable for your design, a separate Python process hosting libmpv is still possible.
The child process would:
• import python-mpv;
• own the mpv.MPV instance;
• receive commands over a pipe;
• serialize them internally;
• send state/events back to the GUI process;
• restart or report failure if libmpv dies.
That does not improve MPV’s internal throughput. It only gives crash containment. The overhead of pipe messages is negligible compared with decoding and seeking, but embedding video into a Qt window across processes is the difficult part. Passing the HWND may work on Windows, but it needs a prototype; the libmpv render API may be safer than cross-process native-window embedding.
So I would treat a helper process as a recovery boundary, not as a performance solution.

• Qt is not the reason MPV must be single-threaded.
• python-mpv does turn ordinary libmpv error codes into exceptions.

• Decode errors are often asynchronous events, not exceptions from loadfile.
• Native crashes cannot be caught in-process.
• One serialized command scheduler is still the right architecture because libmpv itself serializes operations.

If by “scheduler” you mean a complex policy system that coalesces, prioritizes, and cancels commands, I agree: that is unnecessary.
The minimum design is simply:
text
Enable word wrap
Copy
GUI call
   ↓
FIFO command queue
   ↓
one MPV command-pump thread
   ↓
mpv.command_async(...)
   ↓
completion/error event
Every GUI command enters the queue and receives a command ID or Future. Nothing is silently discarded.
Let MPV queue the commands
For commands that must not block the GUI, use MPV’s asynchronous API:
python
Copy
future = mpv_instance.command_async(
    "seek", position, "absolute"
)
The GUI does not wait. The command-pump submits it to MPV, and the completion callback resolves the associated command ID.
This is closer to what you want than a custom coalescing scheduler.
However, there are three important limitations:
1. MPV’s async queue can overflow.
2. Async operations can be reordered relative to other synchronous/asynchronous operations.
3. Every command still passes through MPV’s internal serialized core lock.
The official libmpv API explicitly says that asynchronous calls return results as events and may reorder unless completion is awaited. It also says that multiple threads do not improve throughput because access is ultimately serialized internally. Official libmpv client API
So the queue can be simple, but it still needs command tracking.
“Every command must be caught”
The correct model is that every submitted command completes exactly once with one of these results:
text
Enable word wrap
Copy
SUCCESS
MPV_ERROR
QUEUE_OVERFLOW
SHUTDOWN
CANCELLED_BY_SHUTDOWN
For example:
text
Enable word wrap
Copy
command 421: seek 32.5 seconds
command 422: set volume 80
command 423: load file B
Each one gets a completion result. Even if MPV is shutting down, command 421 should receive SHUTDOWN, not disappear.
The current AVPlay wrapper does not do this. _mpv_call() catches everything and returns None:
mpv_video_player.py (line 64)
That is why the current integration loses the distinction between:
• command rejected;
• command timed out acquiring the lock;
• MPV was already shut down;
• MPV failed to decode;
• command actually succeeded.
Use async commands, not async property access everywhere
Many current calls use synchronous property access:
python
Copy
mpv.pause = False
mpv.volume = 80
mpv.seek(...)
Those can block inside the caller.
The command pump should instead translate them into asynchronous commands:
python
Copy
command_async("set", "pause", False)
command_async("set", "volume", 80)
command_async("seek", position, "absolute")
command_async("loadfile", path)
The MPV event thread then reports the result.
For getters, the GUI should not synchronously ask MPV five times every timer tick. Either:
• send asynchronous get_property requests; or
• maintain a cached state updated by MPV property-observer events.
That does not discard GUI commands. It prevents the GUI thread from blocking on native calls.
The queue cannot make MPV process commands in parallel
If the GUI produces commands faster than MPV can execute them, there are only three possible outcomes:
1. commands wait in a queue;
2. commands are intentionally coalesced;
3. the queue eventually overflows or memory grows.
There is no fourth option that makes MPV execute all of them simultaneously. libmpv itself serializes operations internally.
For your requirement, the safest initial policy would be:
• do not coalesce commands;
• preserve FIFO order in the application queue;
• submit every command asynchronously;
• track every completion;
• report queue overflow explicitly;
• never block the GUI thread;
• when MPV shuts down, resolve every outstanding command with a shutdown error.
Later, individual operations such as seek can optionally use “latest value wins”, but that is an optimization, not a requirement for the basic architecture.
MPV errors versus MPV crashes
Normal MPV failures are catchable:
text

Copy
invalid command       → Python exception
invalid property      → Python exception
load failure          → end-file event with error
audio/video init fail → Python exception or event
event queue overflow  → error/event
But a native crash in libmpv, FFmpeg, a decoder, or a GPU driver is not catchable by Python. No queue design or try/except can recover after an access violation.
The current wrapper makes this worse because:
• it swallows command exceptions;
• it does not properly expose queue-overflow;
• it does not wire MPV’s shutdown event into AVPlay;
• it calls terminate() without guaranteeing that other operations have stopped.
mpv_video_player.py (line 100)
The official libmpv API specifically warns that destruction is unsafe while other calls are still using the same context. Official libmpv client API

Qt is not generally “GUI-thread only”. Queued signals and cross-thread event posting are specifically supported. The problem is direct widget calls.
This current call is direct:

Copy
AVPlay monitor thread
    → _update_current_track()
    → QLabel/QWidget updates

__AV_Player.py (line 233)

You do not need a sophisticated scheduler. You need:
• one FIFO command queue;
• one MPV command-pump thread;
• command_async() for nonblocking submission;

That lets MPV manage its own internal command processing while ensuring that PlayForm never loses track of a GUI request or blocks its interface.
It still cannot protect the application from a genuine native libmpv crash. For that, only a separate process hosting libmpv provides containment. That process would not improve command throughput; it would only allow PlayForm to detect the MPV process dying and recreate it.
