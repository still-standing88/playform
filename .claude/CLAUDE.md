# PlayForm — orientation for coding agents

PlayForm is a desktop media player for audio/video, built with **PySide6** (Qt),
using **mpv** (via `python-mpv`/libmpv) as the playback engine and **Nuitka** to
compile to a standalone Windows executable. Repo: `still-standing88/playform`,
GPL-3.0, publisher "Joybytes". Current version: `1.0.2` (see `src/app_info.py`).
The `mpv-rewrite` branch migrated the backend off VLC/libvlc onto MPV; that
migration is functionally complete (see `git log -- src/av_play`) but ongoing
work is still cleaning up stray VLC-era wording/docs and hardening the MPV
backend (crash handling, COM init, playlist advance races).

The git repo root is the `PlayForm/` folder (this file lives at
`PlayForm/.claude/CLAUDE.md`). `PlayForm/dist/` is a build output directory
(gitignored) — don't confuse it with the source tree.

## Tech stack

- **GUI**: PySide6 6.10.2 + QDarkStyle for theming, Fusion style, custom `theme_manager`.
- **Playback**: `av_play` — in-house media-backend abstraction (`AVPlayer`/`AVMediaInterface`
  in `src/av_play/__AV_*.py`). The live backend is `MPVVideoPlayer`
  (`src/av_play/mpv_video_player.py`), wrapping `python-mpv`/libmpv.
  `src/utilities/mpv_bootstrap.py` / `setup_mpv_binaries()` makes the libmpv binaries
  discoverable at runtime (dev vs frozen/Nuitka paths differ, Windows/macOS/Linux each
  handled separately in `src/utilities/functions.py`).
- **DB**: `peewee`, but **not used as an ORM** — `src/app_db/base_database.py` drives
  `peewee.SqliteDatabase` with raw `execute_sql` calls, WAL mode, and a background
  queue-thread for writes (each writer thread gets its own connection + COM init/uninit
  on Windows). Two handlers: `user_db.py::UserFiles` (favorites/recents/library) and
  `media_db.py::MediaDatabase` (media metadata cache).
- **Downloads/streams**: `yt-dlp` (YouTube), `feedparser` (podcasts),
  `util_download_center/` (fetches/installs external tool binaries like yt-dlp/ffmpeg).
  Internet radio uses `media_core.pyradios` (vendored `pyradios`, not the `radios` pip
  package — see `git log -- src/media_core/pyradios`).
- **FFmpeg wrapper**: `media_core.ffmpeg` — vendored `python-ffmpeg` (was the
  `python-ffmpeg` pip package, imported as `from ffmpeg import FFmpeg`; now vendored the
  same way `pyradios` was, see `git log -- src/media_core/ffmpeg`). **All ffmpeg-graph
  code must import from `media_core.ffmpeg`, never from a pip `ffmpeg` package.**
- **Subtitles**: `pysubs2`, `pycaption`. **Tags/metadata**: `mutagen`, `music-tag`.
- **Build**: `Nuitka` via `pyinvoke` tasks (`build.py`, `tasks.py`, `dist.py`, root
  `invoke_config.py` for shared paths). Windows installer via WiX (`installer/windows/`).
- **Signing**: RSA-4096 keypair at repo root (`private_key.pem` / `public_key.pem`),
  `src/public_key.py` embeds the public key (generated by `scripts/public_key_generator.py`).
  `scripts/sign.py`/`scripts/keygen.py`/`scripts/checksums.py` handle release signing.
- **Custom compiled deps** (not ordinary pip packages, treat as black boxes unless the
  user says otherwise): `AppGuard` (single-instance guard), `SpeechCore` (TTS).

## Entry point & startup (`src/app.py` → `src/app_init.py`)

`main()` in `app.py`: `setup_env()` → `setup_mpv_binaries()` → `install_translation()` →
create `QApplication` → show `LoadingSplash` → then, via `app_init.py` helpers:
`setup_environment()` (frozen vs dev paths, `QT_PLUGIN_PATH`) → `setup_application_style()`
→ `initialize_app_guard()` (single-instance check) → `initialize_modules()` (config, db,
speech engine thread) → `create_main_window()` → local IPC server → hotkeys → `setup_cleanup()`.

**Gotcha**: single-instance/"open this file in the already-running instance" logic is
implemented *twice* — once via a raw `QLocalServer`/`QLocalSocket` protocol in
`app_init.py`, and once via `AppGuard`'s own message-passing (`create_ipc_msg`/`register_msg`).
Both paths are live. If you touch CLI-arg/file-open handling, check both.

## GUI structure

`src/gui/main_window.py` is a large `MainWindow(QMainWindow)` that wires together nearly
every feature module. It delegates to five manager classes in `src/gui/managers/`
(`menu_manager.py`, `toolbar_manager.py`, `dock_manager.py`, `tool_window_manager.py`,
`playlist_handler.py`). **These managers aren't self-contained** — they take
`main_window` in `__init__` and set attributes directly on it (e.g.
`self.main_window.file_menu = ...`), so state is scattered across `MainWindow` rather
than encapsulated in each manager. Expect to grep `main_window.py` for attribute usage
when refactoring a manager.

`src/gui/dialogs/`, `src/gui/prefs_panels/`, `src/gui/recents_favorites/` are more
conventional (dialogs, prefs-dialog tabs, recents/favorites widgets over `app_db.UserFiles`).

## Tools (`src/tools/`)

As of the `tools-rewrite` branch, tools live in per-tool subpackages, not flat
`src/tools/*_ui.py` files (that flat layout is gone — don't recreate it):

- `tools/ffmpeg/` — everything driven by `media_core.ffmpeg`:
  - `batch_converter/` — Source/Convert/Processing/Destination tabbed UI (`ui.py`),
    with `format_capabilities.py` (per-audio-format encoder/option map, sourced from
    `archive/docs/ffmpeg-manuals/ffmpeg-codecs/8-audio-encoders/`) and
    `effects_catalog.py` (the Processing-tab Edits/Filters effect definitions, sourced
    from `archive/docs/ffmpeg-manuals/ffmpeg-filters/8-audio-filters/`) as the source of
    truth for what's offered in the UI — extend those tables rather than hardcoding new
    format/filter strings in the UI layer. `job.py` builds the actual `media_core.ffmpeg`
    command graph and runs it threaded.
  - `media_extractor/` — audio/video/image extraction; reuses `batch_converter`'s
    `AudioConvertPanel`/`VideoConvertPanel` for format options rather than duplicating them.
  - `thumbnail_generator/` — mechanical move of the old tool, behavior unchanged.
- `tools/subtitles/` — `converter_ui.py`, `editor_ui.py`, `handler.py` (was
  `subtitle_*_ui.py` + `subtitle_handler.py` at the `tools/` root).
- `tools/tag_editor/` — `ui.py` (was `tag_editor_ui.py`).
- `tools/speech_converter/` — new tool built on `PySide6.QtTextToSpeech` (see the
  `tts_demo.py` prototype at the repo root for the base API shape). `engine.py` wraps
  `QTextToSpeech` for the cross-platform path and additionally drives `SAPI.SpVoice`/
  `SAPI.SpFileStream` directly via `win32com.client` on Windows for two things Qt's API
  doesn't expose: rendering speech to an audio file (`save_to_file`), and SAPI's
  `<pitch middle="N">` XML markup (a SAPI-specific extension, not part of
  `QTextToSpeech`'s normalized pitch parameter).
- `tools/m4b_tools/` — reserved placeholder only; the Tools menu entry is disabled.
  Scope depends on manuals the user hasn't provided yet (see `TOOLS_REWRITE_PLAN.md`).
- `gui_controls/path_tree_widget.py` — shared file/folder source-tree control (used by
  Batch Converter's Source tab; suitable for reuse by future tools needing the same
  add-files/add-folder-with-format-filter workflow).

Every tool is still wired into the app in exactly one place:
`src/gui/managers/tool_window_manager.py` (`ToolWindowManager.open_*` methods) plus a
matching `QAction` in `src/gui/managers/menu_manager.py`'s `setup_tools_menu()`.

## `app_config/` vs `app_constance/` — not a typo you should fix

- `src/app_config/` = user-mutable runtime state: `prefs.py` (persisted to
  `data/prefs.json`, lightly obfuscated via hexify/dehexify — **not encryption**),
  `key_config.py` (hotkeys), `toolbar_config.py`.
- `src/app_constance/` = static defaults/lookup tables, read-only at runtime:
  `prefs_dict.py` (default prefs schema), `default_keys.py`, `file_filter.py`, `misc.py`,
  `styles.py`.
- `app_constance` is a baked-in misspelling of "app_constants" used as the actual
  **package name** throughout the codebase. It cannot be silently renamed — every
  import site depends on the misspelled name. Don't "fix" it without a deliberate,
  repo-wide rename the user asks for.

## Known in-progress / stale things

- **`src/app_db/_sqlalchemy_backup/`** (untracked): the previous SQLAlchemy
  implementation of the DB layer, kept as a backup after migrating to the current
  peewee-as-sqlite-driver approach. `SQLAlchemy==2.0.46` is still in
  `requirements-runtime.txt` and `build.py` still has Nuitka
  `--nofollow-import-to=sqlalchemy.*` excludes — both are stale leftovers from the
  migration, not evidence SQLAlchemy is still used. Confirm with the user before
  deleting the backup folder or the stale requirement.
- **`scripts/test_device_*.py`, `test_mta_*.py`, `test_ds_*.py`, `debug_audio_devices.py`,
  `_tmp_*.py`** (~30 files, untracked): ad-hoc repro scripts investigating a
  **Windows audio-output-device switching bug**, originally against libvlc and now
  against the MPV backend (COM apartment threading, DirectSound/WASAPI device
  enumeration timing, device persistence across track changes and teardown — see
  commit `679762a` "Initialize COM on the MPV worker thread"). None of this is part
  of the shipped app — it's active debugging scratch work for a specific unresolved
  bug. If asked about audio device switching issues, this is the relevant context
  and prior art.
- **Docs**: `docs/source/en/documentation.md` is the hand-authored source;
  `docs/build/en/documentation.html` is a *compiled* artifact produced by
  `scripts/compile_docs.py` (custom Markdown→HTML pipeline: `Markdown` +
  `mdx_truly_sane_lists` + `markdown-link-attr-modifier` + `nh3` sanitizer — despite
  the `source`/`build` naming, this is not Sphinx). **Edit the `.md` source and
  recompile; never hand-edit the `.html`.**
- **Repo-root scratch files** (`ff.py`, `fff.py`, `tb.py`, `example_app.py`,
  `test_toolbox.py`, `list_control.py`, `list_control_demo.py`, `url_support.py`, etc.):
  prototypes/one-off experiments, not imported by `src/`. Don't treat them as part of
  the app's behavior; ask before deleting since they may be in-progress prototypes
  (e.g. `list_control.py` looks like an unfinished custom list-view widget).

## Build & release workflow

- `invoke_config.py` (repo root) defines shared paths (`SRC_DIR`, `BIN_DIR`, `ROOT_DIR`,
  `ASSETS_DIR`, `SCRIPTS_DIR`) — imported via `from invoke_config import *` in the task
  files below.
- `tasks.py` — dev-facing invoke tasks (`install_req`, `dev_install`, `clear_cache`, `run_app`).
- `build.py` — Nuitka `--standalone --deployment` compile tasks for `src/app.py` (main
  app) and `src/updater.py` (separate standalone updater binary). Has a `--debug-build`
  flag that skips `--remove-output` and does manual `app.dist` cleanup so `app.build`
  (per-module `.c`/`.o` files) survives for cache inspection.
- `dist.py` — release/signing: `keygen` (RSA-4096), `generate_public_key` (writes
  `src/public_key.py`), `checksums`.
- `installer/windows/` — WiX MSI installer (`product.wxs`, `build-msi.ps1`, `app.manifest`).

- Commits must be short and concise.
